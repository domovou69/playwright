# Explorbot Experiment Plan

## Goal

Evaluate [Explorbot](https://github.com/testomatio/explorbot) (v0.5.3, autonomous AI exploratory-testing
agent) as an alternative/complementary way to produce E2E coverage for zedge.net, and compare it against the
manually-curated baseline in `specs/wallpapers.plan.md` (23 scenarios, generated by `playwright-test-planner` +
human review, already automated in `tests/wallpappers/`).

Comparison axes: effort (time + $ cost), coverage (flows/pages chosen), bugs found, and code quality of the
generated tests/POM.

## Isolation rules (must hold for a fair comparison)

- Explorbot gets **no access to this repository**: no `pages/`, no `tests/`, no `specs/*.plan.md`, no this
  conversation's findings (e.g. the WP-29 price=10 bug, the WP-33 accessibility bug, the `SortByType` gaps).
  It only ever sees the live site through its own browser, exactly like a real black-box tester would.
- It runs from a clean `~/.explorbot/` state — no prior knowledge files, no hints about known bugs or filter
  quirks. If it independently rediscovers WP-29 or WP-33, that is a genuine, uncoached finding worth noting.
- No login/auth flows, no purchase completion, no security/fuzzing, no load/performance testing — same
  constraints as `wallpapers.plan.md`. Explorbot doesn't do load/security testing by design anyway; login is
  excluded by scoping its config to guest-accessible pages only.
- Output (specs, POM, report) goes to a **separate, clearly-marked directory** (see below), never merged into
  `pages/` or `tests/wallpappers/` automatically. Any reuse of its output is a deliberate decision made _after_
  the comparison, not part of the experiment.

## Scope (main functional workflows, guest only)

Mirrors the section already covered by the baseline, so the two are comparable:

- Wallpapers list page (`/wallpapers`): cards, header search, category nav
- Filters: Category, Tag, Price, Color, Sort by, Reset All
- Infinite scroll / "Load more"
- Wallpaper detail page
- Free download flow (stop before completion if it requires leaving the guest session)
- Premium purchase gate (stop at the modal — never complete a purchase or log in)

Out of scope (told to Explorbot explicitly via config, not just "hoped"):

- Any authenticated/logged-in area
- Security testing (XSS, SQLi, fuzzing)
- Load/performance testing
- Ringtones / Notification Sounds sections (baseline only covers Wallpapers)

## Model configuration (Groq, free tier)

Decision: run on **Groq**, using Explorbot's own bundled recommendation for that provider (both roles land on
Groq's free-tier models, so the run costs $0 up to rate limits). This trades "it's literally Claude" for
"actually free" — a deliberate call, not the default Anthropic-everywhere plan considered earlier.

| Role                                                | Env var                                                                    | Model                | Why                            |
| --------------------------------------------------- | -------------------------------------------------------------------------- | -------------------- | ------------------------------ |
| model (fast, HTML-heavy)                            | `EXPLORBOT_AI_MODEL=groq/openai/gpt-oss-20b`                               | `openai/gpt-oss-20b` | Groq's recommended fast worker |
| visionModel / agenticModel (planning, verification) | `EXPLORBOT_VISION_MODEL` / `EXPLORBOT_AGENTIC_MODEL=groq/qwen/qwen3.6-27b` | `qwen/qwen3.6-27b`   | Groq's recommended smart role  |

Simplest form: `EXPLORBOT_AI_PROVIDER=groq` fills all three roles from Groq's recommendation automatically —
no need to set the three model vars individually unless overriding one role.

Requires `GROQ_API_KEY` (free signup, no card, rate-limited) in the experiment's `.env`.

Anthropic was considered (Haiku 4.5 for research/execute, Sonnet 5 for plan/verify, no Opus — Explorbot's docs
explicitly advise against a premium model for testing) and is documented here as a fallback if Groq's free-tier
rate limits prove too restrictive for a full run; `npx explorbot plan` (plan-only, no execution) is cheap enough
on Haiku 4.5 to use for a quick cost/quality spot-check without switching providers.

## Setup steps

1. Install: `npx explorbot@latest start https://www.zedge.net/` (or local devDependency, TBD after checking
   how the CLI prefers to be run) — creates `~/.explorbot/sites/zedge.net/` and a local `explorbot.config.js`.
2. Set `ANTHROPIC_API_KEY` (existing project key) and configure the provider/model split from the table above.
3. Edit `explorbot.config.js`: restrict start pages to `/wallpapers` and its sub-pages; exclude login/account
   URLs.
4. Do **not** feed it any knowledge file referencing this repo's tests, POM, or bugs.
5. Run interactive mode first (`/explore`), inspect the test **plan** it proposes, before approving any
   "keep" step that would generate/save tests.

## Decision gate

After step 5, stop and review with the user:

- What scope/scenarios did it propose vs. `wallpapers.plan.md`'s 23?
- Does the proposed plan look worth letting it execute (cost estimate, relevance)?
- Only after explicit go-ahead: let it execute, verify, and keep tests.

## Metrics to collect (for the comparison writeup)

- Wall-clock time and token/$ cost of the Explorbot run
- Number of scenarios proposed vs. kept vs. baseline's 23
- Overlap/gap analysis: which baseline flows it found independently, which it missed, what it found that the
  baseline doesn't cover
- Any bugs/inconsistencies flagged, cross-checked manually (LLM agents produce false positives)
- Subjective code-quality read of its generated Playwright specs/POM vs. `pages/` + `tests/wallpappers/`

### Provider notes (actual, not planned)

- **Groq free tier**: not viable. The only Groq model compatible with Explorbot's `reasoning_effort` param
  (`openai/gpt-oss-20b`) hits its **8000 TPM** cap on the very first research call against `/wallpapers`
  (page needs ~17.9k tokens of context). Other available free Groq models (`allam-2-7b`, `qwen/qwen3.8-27b`)
  don't support `reasoning_effort` at all.
- **Google Gemini (AI Studio) free tier**: works. `gemini-3.1-flash-lite` (fast/vision) + `gemini-3.5-flash`
  (agentic) — Explorbot's own bundled recommendation for the `google` provider. First `plan` run: 50s,
  56K + 6K tokens, $0 (within free daily quota). Running with this from here on.

### Methodology correction (2026-09-28)

The 6 follow-up `--focus` passes above were **not** clean black-box discovery — their wording (search
empty-state, Reset All, price range, deep-link, related section, premium-across-prices) was drawn from this
session's own knowledge of the baseline `wallpapers.plan.md`, not invented by Explorbot. Even the first,
broader focus phrase named specific site features already known from prior analysis. **Explorbot was never run
with zero content hints** — `--focus` is optional but every call here used it. This doesn't invalidate the
scenario count (22 vs. baseline's 23 is still a fair coverage-breadth comparison), but it means the _planning_
side of this experiment measured "Explorbot fleshing out named areas," not "Explorbot deciding the test map
from scratch." True unprompted scope discovery (`plan /wallpapers` with no `--focus`, or `freesail`) was never
tested and would need a separate run to evaluate honestly.

### First execute run (2026-09-28) — flash-lite agentic model

Ran `npx explorbot test <premium-gate-plan> 1` (first scenario: low-tier premium price point). Switched
`agenticModel` to `google/gemini-3.1-flash-lite` beforehand — `gemini-3.5-flash`'s free tier is **20 requests/
day**, already at 11/20 from planning alone; flash-lite has 500 RPD / 15 RPM / 250K TPM headroom.

**Result: passed**, and — with no coaching — **independently rediscovered the WP-33 finding** (console error:
"DialogContent requires a DialogTitle", same defect documented in the baseline). This is the one genuinely
uncoached signal from the whole experiment so far.

**Cost/reliability reality on flash-lite:**

- 732K tokens for **one** scenario (450K cached / 63%), 3m15s wall-clock, 5 separate "Researching..." cycles
  (full DOM re-analysis from scratch each time — every wallpaper detail URL has a unique GUID, so the per-URL
  experience cache never carries over between different wallpapers).
- Hit `AI_APICallError: quota exceeded` (TPM) three times _within this single scenario_; the AI SDK's own
  retry/backoff recovered each time. No client-side rate-limiting exists in Explorbot itself — only the
  provider SDK's built-in retry.
- Bot made 2 wrong guesses (picked free wallpapers thinking they were premium) before finding a working path via
  the "Premium Selects" collection + search — realistic trial-and-error, not a scripted path.
- The **generated test file did not persist reliably**: right after the run, reading
  `output/tests/...premium_purchase....js` showed only the two _failed_ attempts as `Scenario.skip`/`.todo`
  (with narrative `Section()` comments) — not the actual passing scenario the CLI reported as "Successful test".
  By the next check, the file was gone entirely from disk (checked both the local `output/` and
  `~/.explorbot/`) — likely the historian's finalize step never completed cleanly given the mid-run quota
  errors. Test-artifact persistence is not reliable under rate-limit pressure on the free tier.

### Output format: no Page Object Model support

Confirmed by reading the installed package's own source (`src/config.ts`, `src/ai/historian/*.ts` — not
documented on GitHub): Explorbot has **no POM generation** of any kind. `ai.agents.historian.framework:
'playwright' | 'codeceptjs'` (default `codeceptjs`) only switches the _syntax_ of the single flat spec file
written per scenario — locators stay inline as literal ARIA role+text strings discovered during the run
(`{"role":"link","text":"..."}`), never extracted into reusable page-object classes/methods. Switched the
experiment config to `framework: 'playwright'` for future runs, but this only changes syntax, not structure —
the earlier README claim "Generates Playwright or CodeceptJS test specs" refers to CodeceptJS's own Playwright
_browser driver_ (a dependency), not a `@playwright/test`-style code generator with any POM abstraction.

### Positioning, per the tool's own docs (not inferred)

`node_modules/explorbot/README.md`: _"Explorbot needs your knowledge — you guide it with plain-text notes and
domain hints"_; _"point Explorbot at a focused page"_; FAQ _"Can I do the same in Cursor with Playwright MCP?"_
→ _"Good luck running it on CI!"_. The tool is positioned as a **continuous, CI-resident exploration companion**
for an already-deployed CRUD app — accumulating a per-URL "experience" cache (memoized DOM analysis + what
worked) over many long-running sessions — not as a one-shot generator competing with a coding agent
(Claude + Playwright MCP) on single-run code quality. It runs as a fully separate process from a `playwright
test` regression job; the two do not share state or coordinate.

### Verification model: end-of-flow, not step-by-step

Traced the execute run's own log order: all `Execute` steps (the clicks) ran first, then a single `Pilot
analyzing progress...` / `Answering question about screenshot` call produced all three ✔ checks together, at
the very end, against the _final_ screenshot only. The plan file format mirrors this — `## Steps` and `##
Expected` are two separate lists, not interleaved — because that's literally how the agent pipeline works:
Research → Plan → **Execute (all steps)** → **Verify (once, at the end)** → Keep. There is no per-step
assertion. A regression introduced mid-flow (wrong element clicked but the page still lands somewhere
plausible, a toast that appears and auto-dismisses, a race condition) can go undetected as long as the _final_
screen happens to satisfy the Expected list. The baseline `wallpapers.plan.md` format (`expect:` after each
numbered step) checks the path, not just the destination — a real methodological gap for e2e regression
testing, not just a formatting preference.

## Conclusion

- **Coverage breadth**: comparable scenario _count_ achievable (22 vs. 23), but only when the human/Claude
  operator supplies per-area focus hints derived from prior site knowledge — not from zero-input autonomous
  scoping (never actually tested here).
- **Bug-finding**: real positive signal — one genuine, uncoached rediscovery (WP-33) during the single execute
  run performed.
- **Code-artifact quality**: not comparable to the hand-authored `pages/` + `tests/wallpappers/` baseline, and
  structurally cannot become comparable (no POM concept exists in the tool) — output is a flat, ARIA-locator
  script per scenario, and on this run didn't even persist reliably once the run hit rate limits.
- **Verification methodology**: end-of-flow only (see above) — a structural weakness for catching mid-flow
  regressions, independent of model or cost.
- **Cost**: not primarily a model-choice problem — a cheaper/local model changes the dollar cost of the same
  wasteful architecture (blind full DOM re-research per navigation, no locator reuse across pages), it doesn't
  fix code quality or reduce the fundamental per-page research overhead.
- **Fit**: matches the tool's own stated positioning — a long-running CI-resident exploratory companion
  alongside an existing regression suite, not a one-shot alternative to manual-analysis-plus-Claude test
  authoring.

### Why Claude + skills + Playwright MCP outperforms it here, concretely

| Dimension              | Explorbot (this experiment)                                                                                                                               | Claude + skills + Playwright MCP                                                                                                                                                                             |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Locator discovery      | Full DOM/vision "Research" from scratch on every new URL (5 re-research cycles in one scenario; "Fixing N broken locators via AI conversation" each time) | One `browser_snapshot` call returns the structured accessibility tree; no blind re-scraping                                                                                                                  |
| Memory across pages    | Per-URL fingerprint cache — useless for pages with unique IDs in the path (every wallpaper detail page is "new" to it)                                    | Whole-session context persists across the entire task; a locator pattern learned once (e.g. "Buy button") generalizes across all similar pages by the person/agent, not re-discovered per URL                |
| Output artifact        | Flat, single-scenario CodeceptJS/Playwright file, inline ARIA role+text locators, no reuse, no POM; didn't persist reliably once the run hit rate limits  | Typed POM (`pages/*.ts`) + data-driven specs, documented invariants, `@bug`-tagged regression tests with reproduction steps — a maintainable artifact from day one                                           |
| Verification           | End-of-flow only, one vision call against the final screenshot (see above)                                                                                | Per-step `expect()` assertions interleaved with actions, catching mid-flow regressions                                                                                                                       |
| Token cost (measured)  | 732K tokens for **one** scenario (450K cached), 3m15s wall-clock, on the _cheap_ free-tier model                                                          | Not separately re-measured in this experiment, but architecturally avoids the repeated full-page re-research that drove Explorbot's number up — the cost driver is the blind-scraping loop, not model choice |
| Reliability under load | Hit provider TPM quota 3 times within a single scenario; the final "kept" test file vanished after a quota-interrupted historian finalize step            | Single coherent session, file writes are direct and immediate (Edit/Write), not dependent on a multi-agent pipeline finalizing correctly under rate-limit pressure                                           |
| Autonomy               | Needs a human/Claude-supplied feature list and focus hints to produce a plan resembling the baseline's coverage; true zero-hint scoping untested          | Same — needs a human/spec-driven scope — but produces a maintainable result once given one, instead of a disposable trace                                                                                    |

Net: Explorbot's per-page blind-DOM-research loop (not model size) is the actual cost driver, its output has no
reusable structure by design, and its verification step only checks the final screen — three independent,
architectural reasons a directed Claude + Playwright MCP session produces a better artifact per token spent,
for this project's goal of a maintainable e2e POM suite.

Experiment closed at this scope: 22-scenario plan set kept in `output/plans/`, one execute run performed and
documented above. Raw run artifacts (reports, DOM research cache, experience cache) were deleted after
findings were captured here; configs and knowledge file kept in `explorbot-experiment/`.
