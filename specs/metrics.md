## Conventions

Rules only - evidence and history for each lives in the dated `Pipeline log` entries below.

- **Single run, not repeats.** A generated test runs once. A failure is a bug: fix the site plan (`@bug`) or the
  test/POM, don't average it away with `--repeat-each`. Re-run once after a fix to confirm, no more. This is about
  _diagnosis_ (never blindly re-run everything to see if a failure goes away) - it doesn't conflict with
  `retries: 1` in the config, which only re-runs a test that actually failed, once, as a live-site-concurrency
  safety net (see `workers: 3` below). A failure that still fails on its retry is still a bug, investigated the
  same way.
- **Commit granularity for this pipeline:** test file(s) + the POM changes they needed + the matching
  `metrics.md` log line go in one commit, not metrics-after. (The commit workflow itself - never unasked,
  ready-to-paste blocks - is `CLAUDE.md`'s rule; not repeated here.)
- **Batch by file, not by a fixed count.** One `playwright-test-generator` call per target file, covering every
  scenario that belongs there - not a capped "2-3". Still exactly one generator agent at a time: its MCP browser
  tools share a single session with no per-call isolation, so concurrent agents would fight over the same page.
- **Skip the generator for pure recombination.** A scenario that's ~90%+ existing POM methods with nothing new
  to discover on the site: write it directly, run once. Reserve the agent for genuinely new locators/behavior.
- **Overlap verification and generation.** The test runner (`npx playwright test`) and the generator's MCP
  browser are separate sessions and don't collide - run a finished batch's verification in the background while
  generating the next one.
- **Don't debug a green run.** Only write exploratory live-verification scripts once something has actually
  failed.
- **Data-driven cases hold only data, never behavior.** No function fields (`apply`, `run`, `verifyExtra`) in a
  case array - all step logic and POM dispatch live in the `test(...)` body or a named helper it calls
  explicitly (e.g. `applyFilter(app, filter, option)`).
- **POM helper naming: `expect*` for a method that asserts, not just reads.** A method whose body calls
  `expect(...)` and would throw on failure is named `expect<Subject>` (e.g. `expectCardPricesNonIncreasing`),
  not `assert*`/`validate*`/`check*` - `expect` matches the assertion vocabulary already used everywhere else
  in the suite (`await expect(locator)...`), so the call site reads consistently. A method that only reads/returns
  a value with no assertion (e.g. `isCategorySelected`, `getPriceFromValue`) keeps its `is`/`get` prefix as before.

**`dismissCookieBanner` 10s stall on every test, found from a direct human report (2026-09-27 02:35):**

11. `dismissCookieBanner` called `rejectBtn.click({ timeout })` directly on `#didomi-notice-disagree-button` - the exact same locator the auto `rejectCookieConsent` fixture (`fixtures/test.ts`) already has registered via `addLocatorHandler`. Confirmed live via `locator.click`'s call log: Playwright treats the pending direct click as an interceptable action, runs the registered handler first (which clicks the button and removes it), then still waits to perform the _original_ click on that now-gone element - which never reappears, so it silently ate the full `timeout` (10s) via the surrounding `try/catch`, on every single test that calls `WallpapersListPage.open()`. Reproduced 3/3 at ~10.00-10.01s each; this was the "does nothing for 5-7s" the human noticed. Fixed: `dismissCookieBanner` now does `await expect(rejectBtn).toBeHidden({ timeout })` instead of clicking - this still lets the registered handler perform the one real click (a wait, unlike a direct click, doesn't fight the handler for the same element) and resolves as soon as it does. Verified live: ~170-200ms typical, 3/3 runs.

**That same fix regressed the original CI race it was meant to guard, found from a CI run with 16 failures (2026-09-27 04:30):**

12. `toBeHidden()` only _waits_ when the element is currently visible; on a not-yet-visible element it's trivially satisfied and returns immediately - so on a slower environment (CI network, Didomi script not yet loaded when `dismissCookieBanner` runs), it gave zero protection and the banner could still appear later, mid some unrelated action, exactly like the original 2026-09-26 CI race (finding 5) `dismissCookieBanner` was written to fix in the first place. Confirmed live with `page.route('**/*didomi*', ...)` delaying the script 4s: the old `toBeHidden()`-only version let a "click Categories" action through cleanly, then the banner appeared during the subsequent `expect(dialog).toBeVisible()` wait, the fixture's handler intercepted, and the Categories dialog never opened (reproduced with a proper retrying assertion, not a one-shot check). Also tried `rejectBtn.waitFor({ state: 'visible', timeout })` as the natural fix (wait for it to appear, then wait for hidden) - this reintroduced the _original_ 10s stall instead: `waitFor` is, like `.click()`, a retrying wait that itself triggers the handler's interception on the same locator, so it finds the banner, lets the handler hide it, then keeps waiting for a `visible` state that will never recur. Confirmed via `DEBUG=pw:api`: only a one-shot, non-retrying call (`.isVisible()`) avoids triggering the interception at all (confirmed separately: a bare poll loop of `.isVisible()`/`.count()` sat through 13+ seconds with the banner untouched). Fixed: manually poll with `.isVisible()` (safe) until the banner appears or a deadline passes, then `toBeHidden()` (safe once it's confirmed already visible) to wait for the handler's dismissal. Verified live: fast local path back to ~170-190ms (4/4 runs), simulated-slow-CI path correctly waits and keeps the dialog intact (4/4 runs), banner-never-appears path returns well under its timeout, not hung. Local full suite still 31/31; **CI confirmation still needs an actual push**.

**Tried, then reverted - the Didomi-bypass approach regressed CI (2026-09-27 05:00-05:30):**

13. After findings 5, 11 and 12 - three rounds of chasing races around a banner that shows up, then gets reactively dismissed - the human asked directly whether the reactive handler could just be dropped, or whether Didomi has a native way to skip showing the banner at all. It does: Didomi's SDK checks `window.didomiOnReady` (a documented public queue) during its own init and applies whatever consent decision is pushed there before it ever decides to render the notice. Confirmed live: `page.addInitScript(() => { window.didomiOnReady = window.didomiOnReady || []; window.didomiOnReady.push(d => d.setUserDisagreeToAll()); })`, run before every navigation - the banner never appears (3/3), vs. always appearing without it (3/3 control), including with a real dialog interaction right after (2/2, dialog stayed open through a 2s wait). This is different from the `didomi_dcs` cookie/localStorage idea rejected earlier (finding 5) - that meant guessing an opaque, session-tied blob; this uses Didomi's own documented API to state the decision directly. Replaced: the `rejectCookieConsent` `addLocatorHandler` fixture (fixtures/test.ts, renamed `declineCookieConsent`), the `dismissCookieBanner` poll-and-wait helper (src/utils/helper.ts, deleted), and its call in `WallpapersListPage.open()` (deleted) - all of it, with the one init-script fixture.
